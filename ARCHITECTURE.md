# Архитектура AdBeam Person Parser

Статус документа: согласованная архитектура; пилотный путь от импорта клиентского
assessment и необязательной выгрузки Контур до обхода официальных сайтов,
checkpoint, семилистового Excel-экспорта и Windows GUI реализован.

## 1. Назначение и границы продукта

AdBeam Person Parser — локальное Windows-приложение, которое принимает Excel с
компаниями, обогащает записи контактами физических лиц из разрешённых открытых
источников и формирует проверяемый Excel-результат.

Продукт отвечает только за поиск, нормализацию и экспорт контактов. Он не
отправляет письма, не ведёт рекламные кампании, не имитирует вход в социальные
сети и не обходит антибот-защиту.

Основные входы:

- Excel-выгрузка Контур.Компас/Фокус;
- ИНН и/или название компании/бренда;
- необязательные сайт, отрасль и список целевых ролей;
- локальные настройки разрешённых источников и API-ключи через переменные
  окружения или gitignore-нутый локальный конфиг.

Основные выходы:

- Excel с компаниями, контактами, источниками и уверенностью;
- журнал прохождения каждого этапа пайплайна;
- очередь ручного поиска с готовыми ссылками;
- локальный реестр прогресса для безопасного возобновления работы.

## 2. Архитектурные принципы

1. Engine не зависит от tkinter и конкретной отрасли.
2. Источники реализуют единый контракт и не вызывают друг друга напрямую.
3. Vertical-плагин только собирает отраслевую конфигурацию, источники и правила;
   оркестрация остаётся в engine.
4. GUI вызывает application-сервисы и отображает события, но не содержит
   парсинг, скоринг и Excel-логику.
5. Каждый переход пайплайна объясним: сохраняются код причины, сообщение,
   длительность и результат этапа.
6. Данные из сети недоверенные: они валидируются Pydantic-моделями и
   санитайзятся перед экспортом.
7. Повторный запуск идемпотентен для той же компании, версии пайплайна и
   конфигурации.
8. Playwright — отдельный необязательный fallback, а не скрытая зависимость
   обычного HTTP-пути.
9. Любой сетевой вызов имеет таймаут, ограниченные ретраи и rate limit по хосту.
10. Персональные данные имеют происхождение, дату сбора и управляемое удаление.

### 2.1 Технологическая база

- Python 3.12+;
- Pydantic для моделей и настроек;
- openpyxl для Excel;
- httpx, tenacity и selectolax для HTTP, retry и HTML-парсинга;
- SQLite из стандартной библиотеки для checkpoint-реестра;
- tkinter для GUI;
- pytest для всех уровней автоматических тестов;
- PyInstaller для Windows `.exe`;
- Playwright только как необязательный fallback конкретного плагина.

## 3. Слои и зависимости

```text
tkinter GUI
    |
    v
application services (запуск, отмена, прогресс, удаление данных)
    |
    v
engine ---------------------------------------------------+
  models, orchestration, scoring, policy, persistence     |
    |                                                     |
    +--> source plugin contract <--- source plugins       |
    |                              (site, registry, etc.)  |
    |                                                     |
    +--> vertical contract <------- vertical plugins -----+
    |
    +--> infrastructure
         Excel, HTTP, rate limits, optional browser, SQLite, logging
```

Допустимое направление импорта:

```text
gui -> application -> engine contracts/models
verticals -> engine contracts/models
sources -> engine contracts/models + infrastructure interfaces
infrastructure -> engine models/interfaces
```

Engine не импортирует GUI, конкретный source-плагин или конкретный vertical.
Регистрация реализаций выполняется в composition root при запуске приложения.

## 5. Основные модели данных

Все перечисленные модели реализуются через `pydantic.BaseModel`. Модели не
содержат сетевых вызовов, работы с Excel или tkinter.

### 5.1 Компания и идентичность бренда

`CompanyInput`:

- `input_row_id`: стабильный идентификатор строки импорта;
- `inn`: нормализованный ИНН или `None`;
- `legal_name`: название юрлица;
- `brand_name`: известный бренд или `None`;
- `website`: исходный сайт или `None`;
- `industry`: отрасль или `None`;
- `kontur_fields`: только разрешённые дополнительные поля импорта.

`CompanyCard` — изменяемое в ходе пайплайна представление компании:

- исходные поля;
- нормализованные идентификаторы;
- найденные домены и социальные страницы компании;
- `brand_identity`;
- целевые роли;
- накопленные контакты и доказательства.

`BrandIdentity`:

- юридическое лицо и ИНН;
- бренд/группа компаний;
- основной домен;
- связь `legal_entity -> brand`;
- источник связи и уверенность;
- альтернативные названия и домены.

### 5.2 Контакт и доказательство

`ContactRecord`:

- `contact_id`: стабильный UUID;
- `company_key`;
- `full_name`, `job_title`, `normalized_role`;
- `emails`, `phones`, `social_profiles`;
- `source_refs`: ссылки на доказательства;
- `collected_at` и необязательный `observed_at`;
- `confidence_score` от 0 до 100;
- `confidence_level`: `LOW`, `MEDIUM`, `HIGH`;
- `verification_status`: `UNVERIFIED`, `CORROBORATED`, `CONFLICTED`;
- `is_personal_data`: всегда `true` для ФИО и персональных каналов;
- `erased_at`: заполняется при удалении записи.

`Evidence`:

- `evidence_id`, `source_id`, `source_kind`;
- URL или идентификатор локального источника;
- дата сбора;
- извлечённый факт в минимально необходимом объёме;
- идентификаторы компании, которыми подтверждено совпадение;
- оценка надёжности источника;
- хеш исходного фрагмента для дедупликации;
- срок/политика хранения.

Полные HTML-страницы по умолчанию не сохраняются. Для диагностики допускаются
только явно включённые временные артефакты в gitignore-нутой папке с политикой
очистки.

### 5.3 Результат source-плагина

`SourceResult`:

- `source_id` и версия плагина;
- `outcome`: `FOUND`, `PARTIAL`, `NOT_FOUND`, `SKIPPED`, `FAILED`;
- найденные контакты и доказательства;
- безопасные изменения `CompanyCard`;
- `reason_code` и человекочитаемое `reason_message`;
- `continue_reason`: почему требуется следующий этап;
- метрики: длительность, число запросов, число просмотренных страниц;
- классифицированная ошибка без секретов и лишних персональных данных.

`PipelineEvent`:

- `run_id`, `company_key`, `step_id`, порядковый номер;
- время начала/окончания;
- состояние до и после этапа;
- outcome и reason code;
- текущая полнота покрытия;
- безопасные технические метрики.

### 5.4 Итог компании

`CompanyResult`:

- финальная карточка компании;
- дедуплицированные контакты;
- `resolution_status`: `RESOLVED`, `PARTIAL`, `MANUAL_REQUIRED`, `FAILED`;
- какие роли/каналы найдены и какие отсутствуют;
- история этапов;
- список конфликтов и предупреждений.

## 6. Контракт плагинов

Source-плагин имеет единый интерфейс:

```python
class SourcePlugin(Protocol):
    metadata: SourceMetadata

    def is_applicable(self, context: PipelineContext) -> Applicability: ...
    def execute(self, context: PipelineContext) -> SourceResult: ...
```

`SourceMetadata` задаёт стабильный ID, версию, тип источника, уровень
надёжности, требуемые настройки, поддерживаемые отрасли и наличие сетевого
доступа.

Инварианты контракта:

- плагин не пишет Excel и не обновляет GUI;
- плагин не решает, какой конкретно плагин вызвать следующим;
- плагин сообщает факты и объяснение результата;
- оркестратор применяет общую routing policy;
- исключение одного источника не уничтожает уже собранный результат;
- `FAILED` отличается от честного `NOT_FOUND`;
- `SKIPPED` всегда содержит причину: нет сайта, источник выключен, нет ключа,
  источник неприменим к отрасли и т. п.;
- результат проходит Pydantic-валидацию до записи checkpoint.

Vertical-плагин имеет интерфейс:

```python
class VerticalPlugin(Protocol):
    metadata: VerticalMetadata

    def source_plan(self, settings: RunSettings) -> list[SourcePlugin]: ...
    def role_taxonomy(self) -> RoleTaxonomy: ...
    def scoring_adjustments(self) -> ScoringPolicy: ...
```

Первый обязательный vertical — `generic`. `developers` добавляет отраслевой
официальный реестр перед закупками. Новая отрасль добавляется без изменений
оркестратора и GUI.

## 7. Дерево решений пайплайна

Пайплайн работает отдельно для каждой компании. Он накапливает результаты,
а не затирает менее свежими находками более надёжные данные.

```text
START
  |
  v
[Валидация входа]
  |-- нет ИНН, названия и бренда ----------------------> INVALID_INPUT
  |-- достаточно данных
  v
[1. Импорт Контур]
  |-- руководитель/контакты найдены --> сохранить evidence и оценить coverage
  |-- сайт/контакты отсутствуют ------> CONTINUE: KONTUR_DATA_INCOMPLETE
  v
[2. Сопоставление юрлица и бренда]
  |-- бренд/группа подтверждены ------> использовать бренд и домен далее
  |-- связь не подтверждена ----------> продолжить с исходным юрлицом
  |-- несколько равных кандидатов ----> отметить конфликт, не угадывать
  v
[3. Обход известного сайта]
  |-- сайта нет ----------------------> CONTINUE: WEBSITE_UNKNOWN
  |-- сайт недоступен/TLS error ------> CONTINUE: WEBSITE_UNAVAILABLE
  |-- контакты найдены ---------------> merge + dedupe + score
  |-- сайт есть, контактов нет --------> CONTINUE: WEBSITE_NO_CONTACTS
  v
[Проверка покрытия]
  |-- нужные роли и канал связи найдены с достаточной уверенностью --> RESOLVED
  |-- покрытие неполное
  v
[4a. Официальный отраслевой реестр]
  |-- неприменим ---------------------> SKIPPED: NO_VERTICAL_REGISTRY
  |-- найдено ------------------------> merge + coverage
  v
[4b. Госзакупки]
  |-- нет участия/контакта -----------> CONTINUE: PROCUREMENT_NO_CONTACT
  |-- найден контакт -----------------> merge + coverage
  v
[4c. Бизнес-справочники]
  |-- найдено ------------------------> merge + coverage
  |-- ничего -------------------------> CONTINUE: DIRECTORY_NO_CONTACT
  v
[4d. hh.ru]
  |-- разрешённый открытый материал найден -> merge + coverage
  |-- нет результата -----------------> CONTINUE: HH_NO_CONTACT
  v
[Проверка покрытия]
  |-- достаточно ---------------------> RESOLVED
  |-- сильные источники результата не дали
  v
[5a. Деловые медиа / события]
  v
[5b. Публичные страницы компании в соцсетях]
  v
[5c. WHOIS домена]
  |-- только разрешённые публичные данные; низкий базовый trust
  v
[Финальная проверка покрытия]
  |-- найден actionable contact ------> RESOLVED или PARTIAL
  |-- контакта нет
  v
[6. Ручная очередь]
  |-- создать поисковые ссылки по компании и целевой роли
  v
MANUAL_REQUIRED
```

Текущая реализация шага 2 использует только детерминированные признаки:

1. уникальный канонический домен;
2. общий домен плюс нормализованное название для выбора одного из нескольких
   юрлиц;
3. уникальное название после удаления организационно-правовой формы.

Если общий домен принадлежит нескольким строкам Контур и название не разрешает
конфликт, результат получает `AMBIGUOUS_DOMAIN_MATCH`. Если одинаковое название
соответствует нескольким ИНН — `AMBIGUOUS_NAME_MATCH`. Fuzzy-сходство строк само
по себе не создаёт связь и может использоваться только для ручной очереди.

### 7.1 Правило остановки

По умолчанию автоматические этапы останавливаются, когда одновременно:

- найдена хотя бы одна целевая роль либо подтверждён руководитель;
- есть хотя бы один пригодный канал связи;
- итоговая уверенность контакта не ниже настраиваемого порога;
- нет неразрешённого конфликта идентичности компании.

Порог и требуемые роли задаются `RunSettings`, а не прошиваются в источниках.
Режим «полное обогащение» может продолжать сильные структурированные источники
для подтверждения уже найденного контакта. Слабоструктурированные источники по
умолчанию запускаются только при отсутствии достаточного результата выше.

Для assessment по застройщикам базовыми целевыми ролями считаются `MARKETING` и
`SALES` (включая коммерческого директора). Результат `RESOLVED` возможен только
при наличии целевого ЛПР с достаточной уверенностью и персонального email или
телефона. ФИО без персонального канала либо общий телефон/email компании дают
`PARTIAL`, но не останавливают дальнейший поиск. Конфликтный ЛПР получает низкую
стартовую уверенность и не проходит порог без нового подтверждения.

### 7.2 Ошибки и отмена

- Ошибка одной компании не останавливает пакет.
- Ошибка источника записывается как `FAILED`, после чего routing policy решает,
  безопасно ли продолжать.
- Фатальные ошибки входного/выходного файла останавливают запуск до обработки.
- Отмена пользователем кооперативная: текущая ограниченная операция завершается,
  checkpoint фиксируется, новые этапы не стартуют.

## 8. Сопоставление, дедупликация и уверенность

### 8.1 Ключ компании

Приоритет стабильного ключа:

1. нормализованный ИНН;
2. подтверждённый домен + нормализованное юрлицо;
3. нормализованное название + регион;
4. хеш значимых исходных полей и ID строки как временный ключ.

Смена временного ключа на подтверждённый выполняется транзакционно с сохранением
связи между ключами.

### 8.2 Дедупликация контактов

Сначала сравниваются нормализованные email/телефон, затем ФИО + компания + роль.
Сырые значения сохраняются в evidence, каноническое значение — в контакте.
Конфликтующие должности или компании не склеиваются молча: создаётся конфликт,
который виден в Excel.

### 8.3 Скоринг

Скоринг детерминированный и тестируемый. Он складывается из:

- базовой надёжности типа источника;
- точности совпадения ИНН/юрлица/бренда/домена;
- явности связи `ФИО + должность + компания`;
- наличия пригодного канала связи;
- свежести наблюдения;
- подтверждения независимым источником;
- штрафов за конфликт, косвенное упоминание или устаревшие данные.

Ориентировочные базовые уровни до корректировок:

| Источник | База |
|---|---:|
| Контур-выгрузка / официальный отраслевой реестр | 90 |
| Официальный сайт компании | 85 |
| Документы госзакупок | 80 |
| Бизнес-справочник | 65 |
| Публичная вакансия/страница работодателя | 60 |
| Деловое медиа или отраслевое событие | 50 |
| Публичная страница компании в соцсети | 45 |
| WHOIS | 30 |

Число не обозначается как «проверенное», если оно рассчитано только эвристикой.
В Excel отдельно выводятся score, level и причины score.

## 9. Идемпотентность и возобновление

Для checkpoint-реестра предлагается локальная SQLite из стандартной библиотеки,
а не Excel. Причины: транзакции, точечное обновление после каждого этапа,
дедупликация, безопасное возобновление и управляемое удаление персональных
данных. Excel остаётся форматом импорта и конечного экспорта.

Реализованный registry хранит валидированный JSON `SourceResult` по ключу
`run_id + company_key + source_id + source_version + config_hash`. Успешные,
частичные, пустые и пропущенные результаты восстанавливаются без повторного
сетевого вызова. `FAILED` не кэшируется и при возобновлении запускается снова.
Операция удаления по `company_key` очищает все checkpoint этой компании во всех
запусках.

База размещается в пользовательском каталоге данных приложения либо по пути из
локальных настроек; внутри репозитория она не создаётся.

Ключ выполнения:

```text
input_fingerprint + company_key + pipeline_version + effective_config_hash
```

После каждого этапа в одной транзакции сохраняются:

- результат плагина;
- контакты и evidence;
- событие перехода;
- следующий этап;
- статус компании.

При повторном запуске:

- завершённые компании с тем же ключом выполнения не пересчитываются;
- незавершённая компания продолжается с первого незавершённого этапа;
- изменение версии плагина или значимой настройки инвалидирует только
  зависимые этапы;
- пользователь может явно запросить полный пересчёт;
- экспорт повторно строится из согласованного состояния и потому идемпотентен.

Предлагаемые таблицы: `runs`, `companies`, `step_runs`, `contacts`, `evidence`,
`contact_evidence`, `pipeline_events`, `erasure_requests`, `schema_migrations`.

## 10. Excel I/O

### 10.1 Импорт

- Заголовки Контур-файлов сопоставляются через конфигурируемые алиасы.
- Перед запуском показывается анализ: лист, найденные колонки, число строк,
  ошибки и небольшой preview.
- ИНН читается как строка и нормализуется без потери ведущих нулей.
- Неизвестные колонки не теряются: они могут быть перенесены в итоговый лист,
  но не попадают автоматически в модели персональных данных.
- Формулы читаются безопасно как значения; макросы не исполняются.

#### 10.1.1 Подтверждённый формат Контур.Продаж

На предоставленном примере подтверждён лист `Контрагенты` с заголовками в
первой строке. Минимально обязательные колонки для запуска — `Наименование` и
`ИНН`; остальные поля импортируются при наличии через таблицу алиасов.

| Группа | Колонки Контур | Назначение в модели |
|---|---|---|
| Идентификаторы | `Наименование`, `ИНН`, `КПП`, `ОГРН` | компания и тип субъекта |
| Регистрация | `Дата регистрации`, `Адрес`, `Регион регистрации`, `Статус`, `Реестр МСП` | профиль компании |
| Руководитель | `ФИО руководителя`, `Должность руководителя` | исходный person contact |
| Минимизация ПД | `ИННФЛ руководителя` | не сохраняется: для поиска контакта поле не требуется |
| Каналы | `Номер телефона`, `Электронная почта` | company-scoped каналы, без ложной привязки к руководителю |
| Ссылки | `Карточка в Фокусе`, `Ссылка на сайт` | hyperlink target с fallback на текст ячейки |
| Деятельность | `Основной вид деятельности`, `Другие виды деятельности`, `Полученные лицензии` | профиль и списки признаков |
| Показатели | `Выручка`, `Баланс`, `Чистая прибыль/ убыток`, `Арбитраж (ответчик)`, `Количество сотрудников` | финансовый и операционный профиль |
| Прочее | `Филиалы`, `Количество филиалов`, `Источник`, `Название сегмента` | метаданные импорта |

Правила, подтверждённые примером:

- ИНН, КПП и ОГРН читаются как строки и проверяются по длине; ИНН также проходит
  контрольную сумму;
- по длине ИНН различаются юрлицо и индивидуальный предприниматель;
- для ИП при пустом поле руководителя ФИО владельца извлекается из
  `Наименование`, но исходное наименование не изменяется;
- телефоны и email могут содержать много значений с разделением переводами
  строк, поэтому извлекаются regex и дедуплицируются после нормализации;
- телефоны/email из этих колонок считаются контактами компании, а не личными
  каналами руководителя, пока источник явно не подтвердит персональную связь;
- в `Карточка в Фокусе` и `Ссылка на сайт` приоритет имеет target настоящей
  Excel-гиперссылки;
- локальный абсолютный путь к клиентскому файлу и значения строк не попадают в
  технический лог; для идемпотентности сохраняются имя файла и SHA-256.

#### 10.1.2 Клиентский assessment застройщиков

Подтверждён формат из двух связанных листов:

- `Ростовская область` — одна строка на бренд, контекст ЕРЗ/ЕИСЖС, сайт,
  company-scoped телефоны отдела продаж, коммерческий скоринг и TIR;
- `ЛПР 2026 verified` — нормализованные ФИО, роли, альтернативные ЛПР,
  статусы актуальности и ссылки на подтверждения.

Связь выполняется по колонке `Строка`, которая указывает номер строки основного
листа, и дополнительно подтверждается точным нормализованным названием компании.
При конфликте контакт не присоединяется автоматически и создаётся import issue.

В assessment нет обязательного структурированного ИНН. До merge с Контуром
используется временный ключ в порядке `ID ЕРЗ -> домен -> хеш бренда и региона`.
Числовые фрагменты URL и ID ЕРЗ не интерпретируются как ИНН. TIR импортируется
как приоритет лида и не влияет напрямую на confidence конкретного контакта.

Телефоны из колонки отдела продаж сохраняются только как company-scoped.
Десятизначный региональный формат разрешён строго для этой доверенной колонки;
при извлечении с веб-страниц сохраняется более строгий шаблон, чтобы не принять
ИНН за телефон. Все исходные колонки основной строки сохраняются в типизированной
карточке как source fields для последующего экспорта и аудита.

### 10.2 Экспорт

Предлагаемые листы:

1. `Компании` — одна строка на входную компанию и итоговый статус.
2. `Контакты` — одна строка на контакт, роль, каналы, score и источники.
3. `Источники` — evidence и даты сбора без лишнего содержимого страниц.
4. `Журнал` — этапы, outcome, reason code, длительность и метрики.
5. `Ручная очередь` — незакрытые компании и поисковые гиперссылки.
6. `Сводка` — конверсия по этапам и распределение статусов.

Для assessment реализован отдельный атомарный экспорт из семи листов:
`Сводка`, `Компании`, `Контакты`, `Источники`, `Журнал`, `Ручная очередь` и
`Исходные данные`. Последний лист сохраняет исходные поля отдельно от
нормализованного результата. Сводка считает статусы и checkpoint hits формулами
по результирующим листам, а не дублирует захардкоженные числа.

Запись атомарная:

1. сформировать уникальный временный `.xlsx` в каталоге целевого файла;
2. закрыть workbook;
3. повторно открыть временный файл через `openpyxl` в read-only режиме и
   проверить обязательные листы/заголовки;
4. закрыть проверочный workbook;
5. выполнить `os.replace(temp_path, target_path)`;
6. при ошибке сохранить старый целевой файл и удалить только известный temp.

Перед записью любой строки:

- удалить запрещённые XML-символы через `ILLEGAL_CHARACTERS_RE`;
- ограничить значение 32767 символами;
- защититься от formula injection: строки, начинающиеся с `=`, `+`, `-` или
  `@`, записывать как текст, если поле не является создаваемой приложением
  формулой/гиперссылкой;
- не помещать секреты и сырые исключения в ячейки.

## 11. HTTP, ретраи и вежливый скрапинг

Один централизованный `HttpClient` инкапсулирует `httpx.Client`:

- TLS verification всегда включена, `verify=False` запрещён тестом/линтером;
- connect/read/write/pool timeout задаются явно;
- редиректы ограничены;
- ретраи `tenacity` только для временных сетевых ошибок и 429/5xx;
- небольшое число попыток с экспоненциальной задержкой и jitter;
- `Retry-After` учитывается;
- лимиты соединений и rate limiter работают по хосту;
- User-Agent идентифицирует приложение без маскировки под браузер;
- размер ответа ограничивается до парсинга;
- разрешены только `http`/`https`, внутренние и локальные адреса блокируются,
  чтобы исключить SSRF через данные Excel;
- URL, токены и персональные данные редактируются в технических логах.

Приоритет: официальные API/реестры, затем публичные страницы. Прямой скрапинг
поисковой выдачи не является основным механизмом. Правила сайтов, robots.txt и
условия использования учитываются конфигурацией источника.

Playwright вызывается только если плагин явно поддерживает browser fallback и
обычный HTTP объективно не получил содержимое. Логин, CAPTCHA solving и обход
защиты запрещены.

## 12. GUI и многопоточность

GUI состоит из небольших views и controllers. Фоновая обработка выполняется
в worker thread; tkinter не вызывается из worker thread.

Поток событий:

```text
worker -> thread-safe Queue[UiEvent] -> dispatcher -> root.after(...) -> views
```

GUI отвечает за:

- выбор и предварительную проверку входного Excel;
- выбор vertical, ролей, режима и выходного пути;
- запуск, отмену и возобновление;
- отображение общего и построчного прогресса;
- отображение безопасных ошибок;
- открытие готового файла;
- запуск операции удаления персональных данных.

Контроллер не содержит сетевого и Excel-кода. Закрытие окна при активной задаче
инициирует кооперативную отмену и ждёт только ограниченное время; checkpoint уже
должен быть консистентным.

## 13. Персональные данные и удаление

`PiiErasureService` принимает селектор субъекта: `contact_id`, точный email,
телефон или ФИО + company key. Перед изменением он строит preview совпадений.

После подтверждения в одной транзакции:

- контакт и связующие записи удаляются либо необратимо обезличиваются согласно
  выбранной политике;
- evidence очищается от персонального фрагмента, если он больше не нужен другим
  контактам;
- checkpoint инвалидируется так, чтобы удалённый контакт не вернулся из кеша;
- в журнале удаления остаются только ID запроса, время, основание и счётчики,
  но не сами удалённые данные.

Для созданного приложением Excel доступна операция безопасной пересборки без
удалённого контакта. Уже скопированные пользователем файлы приложение не может
изменить автоматически; это явно сообщается в отчёте удаления.

Минимизация данных:

- хранить только сведения, необходимые для результата и доказуемости;
- даты сбора обязательны;
- диагностические артефакты имеют срок хранения и команду очистки;
- retention period задаётся локальной настройкой;
- юридическое основание обработки и допустимость конкретного источника остаются
  ответственностью оператора и должны быть отражены в README/интерфейсе.

## 14. Настройки и секреты

`config.example.json` содержит только документированные безопасные значения.
Фактические секреты читаются из переменных окружения или локального файла,
исключённого из Git.

В репозиторий не попадают:

- `.env`, `*.local.json`, `*.settings.json`;
- `output/`, `artifacts/`, базы состояния и browser profiles;
- реальные `.xlsx`, `.xls`, `.xlsm`, `.csv` и `.tsv` клиентов;
- логи с пользовательскими данными;
- сборочные каталоги и готовые `.exe` кроме отдельно согласованного release flow.

Настройки валидируются Pydantic-моделью до запуска. Сообщение об ошибке называет
отсутствующий параметр, но никогда не печатает значение секрета.

## 15. Наблюдаемость и метрики

Для каждого источника считаются:

- применимость и число запусков;
- `FOUND/PARTIAL/NOT_FOUND/SKIPPED/FAILED`;
- доля компаний, впервые разрешённых на этом этапе;
- добавленные и подтверждённые контакты;
- среднее время, число запросов и retry;
- причины переходов на следующий этап;
- доля ручной очереди.

Технический лог — структурированный и обезличенный. Пользовательский журнал в
Excel содержит объяснимые reason codes. Нельзя выводить полные HTML, токены,
персональные query parameters и произвольные тела ответов.

## 16. Тестовая стратегия

Тесты создаются вместе с модулем, а не отдельной завершающей фазой.

Обязательные unit-тесты:

- нормализация ИНН, email, телефона, ФИО и URL;
- regex-извлечение контактов, ложноположительные и граничные случаи;
- санитайзинг XML, лимит Excel и formula injection;
- сопоставление бренда и обработка неоднозначности;
- дедупликация и конфликты контактов;
- детерминированный скоринг со всеми бонусами/штрафами;
- routing tree для каждого outcome/reason code;
- rate limiter, retry policy и запрет retry для постоянных ошибок;
- ручные поисковые ссылки и их URL-кодирование;
- GUI dispatcher без прямого вызова tkinter из worker.

Интеграционные тесты под `pytest`:

- синтетический Excel -> mocked pipeline -> атомарный Excel;
- повреждение temp-файла не заменяет существующий результат;
- падение после каждого этапа и корректное resume без повторных вызовов;
- изменение версии плагина инвалидирует нужный checkpoint;
- удаление контакта очищает состояние и пересобранный экспорт;
- одна упавшая компания не останавливает пакет.

Все HTTP-вызовы используют `httpx.MockTransport` или mocks. Playwright также
мокается; тесты не обращаются к реальным сайтам. Фикстуры не содержат реальных
клиентских или персональных данных.

## 17. Сборка Windows `.exe`

PyInstaller запускается PowerShell-скриптом по staging-схеме:

1. проверить виртуальное окружение и зависимости;
2. собрать в timestamped staging directory;
3. проверить наличие ожидаемых модулей/ресурсов в архиве;
4. выполнить smoke test процесса с диагностическим флагом;
5. скопировать в pending-файл;
6. сравнить SHA-256 staging и pending;
7. убедиться, что целевой `.exe` не запущен;
8. переместить предыдущую версию в backup;
9. установить pending и повторно проверить SHA-256;
10. при ошибке восстановить backup.

В `subprocess` используются только списки аргументов и `shell=False`. Пути
строятся относительно корня проекта/скрипта, а не пользовательского компьютера.
Playwright и браузерные бинарники не включаются в базовую сборку, пока реальный
источник не докажет необходимость fallback.

## 19. Архитектурные решения для согласования

Предлагается утвердить следующие решения до начала реализации:

1. SQLite используется как внутренний checkpoint-реестр; Excel остаётся
   пользовательским входом и выходом.
2. Первый vertical — `generic`; отраслевой `developers` подключается отдельным
   плагином, когда согласован конкретный реестр/API.
3. Пайплайн останавливается по coverage policy, а не просто после первой
   найденной строки.
4. Слабые источники запускаются только при недостаточном результате сильных.
5. Score детерминирован и объясним; найденные факты и уверенность разделены.
6. Полные HTML-страницы по умолчанию не сохраняются.
7. Browser fallback выключен по умолчанию.
8. Удаление персональных данных реализуется до подключения внешних источников,
   чтобы все последующие плагины соблюдали единый lifecycle.

Перед реализацией также потребуется уточнить, не меняя базовую архитектуру:

- пример обезличенной выгрузки Контур для точной карты колонок;
- первый целевой vertical и перечень официальных API/реестров;
- роли по умолчанию и минимально достаточный канал связи;
- доступные API-ключи и ограничения лицензий источников;
- желаемый срок хранения checkpoint и диагностических артефактов.
