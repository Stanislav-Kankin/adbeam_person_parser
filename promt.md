# Промпт для Codex: десктоп-приложение для обогащения контактов B2B

## Роль и контекст

Ты работаешь как старший Python-разработчик, который строит новый проект с нуля.
Проект — desktop-приложение (Windows, .exe), по архитектурному духу похожее на
референсный проект `adbeam_wb_marketguru_parser` (Excel на входе → пайплайн
обогащения → Excel на выходе → tkinter GUI → сборка в .exe через PyInstaller),
но это **новый, отдельный, чистый репозиторий**, не форк и не расширение старого.

Перед тем как писать код — напиши `ARCHITECTURE.md` с планом модулей и деревом
решений пайплайна (см. ниже) и покажи мне на согласование. Только после
подтверждения переходи к реализации, модуль за модулем, с тестами сразу же,
а не «потом».

## Цель продукта

Приложение принимает от пользователя Excel-выгрузку Контур с обязательными
наименованием и валидным ИНН по каждой компании, прогоняет записи через цепочку
источников и на выходе отдаёт Excel с найденными
контактами (ФИО, должность, email, телефон, соцсети), статусом по каждой строке,
источником, откуда взят каждый контакт, и уровнем уверенности.

Это НЕ веб-сервис и не SaaS с своей отправкой писем — это локальный инструмент
для этапа "найти контакт", результат экспортируется в Excel и уже дальше
руками/другими сервисами (например Instantly/Smartlead) льётся в рассылку.

## Пайплайн (дерево решений), которое нужно реализовать

Каждый источник — отдельный модуль/плагин с одинаковым интерфейсом
(вход: карточка компании, выход: список найденных контактов + метаданные
источника + причина, почему пошли дальше по цепочке, если ничего не нашли).

1. **Импорт стартовых данных.** Пользователь заранее выгружает данные по
   компаниям из Контур.Продаж в Excel — это единственный обязательный вход и
   считается самым надёжным источником (ФИО руководителя, телефон/email из
   ФНС, наличие сайта, признаки вакансий/тендеров, если Контур их показывает).
   Строки без валидного ИНН и повторные строки того же ИНН не обрабатываются.
2. **Фиксация идентичности.** Единственный автоматический ключ компании —
   нормализованный валидный ИНН из Контур. Название, бренд, домен, внешний ID и
   числа из URL могут использоваться как контекст поиска, но никогда не
   создают и не меняют идентичность юридического лица.
3. **Обход сайта компании** (если сайт известен): найти контактную
   страницу, вытащить email/телефон/соцсети через regex по HTML — по духу
   как `site_audit.py` / `icp_autosearch.py` в референсном проекте.
4. **Внешние структурированные источники** (в порядке надёжности, выше —
   надёжнее): официальные реестры и открытые API отрасли (если для отрасли
   есть такой реестр, аналогичный ЕИСЖС для застройщиков) → госзакупки
   (если компания участвовала в тендерах — контактное лицо обязательный
   реквизит заявки) → бизнес-справочники (2ГИС, Яндекс Бизнес) → hh.ru
   (текст вакансий + резюме сотрудников компании с нужной должностью).
5. **Слабоструктурированные источники** (ниже надёжность, только если
   выше ничего не дало): локальные деловые медиа / vc.ru / отраслевые
   события — цитаты и упоминания ФИО+должности; соцсети компании;
   whois домена, если домен есть, но неактивен.
6. **Очередь на ручной докрут.** Если автоматика ничего не нашла — не
   выдавать пустую строку, а сформировать для оператора готовые
   поисковые ссылки под нужную роль (по аналогии с `conference_contacts.py`
   из референсного проекта), чтобы человек быстро добил вручную.

Каждый шаг должен логировать, почему пайплайн пошёл дальше (не нашли
сайт / нашли сайт, но без контактов / и т.д.) — это нужно для подсчёта
метрик по каждому этапу воронки (на каком шаге в среднем резолвится
компания), а не только финального успеха/неуспеха.

## Архитектурные требования

- **Engine отдельно от vertical-plugin отдельно от GUI.** Общая логика
  (чтение/запись Excel, HTTP-клиент с таймаутами/ретраями, модели данных,
  оркестратор пайплайна) — в одном слое. Источники данных (шаги пайплайна
  выше) — независимые плагины с одинаковым интерфейсом, чтобы можно было
  добавлять новые отрасли/источники, не трогая остальное.
- **Никаких God-классов.** GUI не должен быть одним классом на 2000+ строк,
  как в референсном проекте. Разделяй по слоям: отдельно построение UI,
  отдельно обработчики событий, отдельно бизнес-логика (она вообще не
  должна знать про tkinter).
- **Все модели данных — через pydantic**, с чёткими типами, как в
  референсном проекте (`models.py` там сделан аккуратно — ориентируйся на
  этот стиль).
- **Идемпотентность.** Пайплайн должен уметь продолжить с того места, где
  прервался (сбой сети, закрытие программы), не пересчитывая заново уже
  обработанные компании — используй паттерн реестра "уже обработано" по
  аналогии с `seller_history` в референсном проекте.

## Технологический стек

Python 3.12+, `openpyxl` (Excel), `httpx` (HTTP-клиент), `pydantic`
(модели), `tenacity` (ретраи), `selectolax` (парсинг HTML), `tkinter`
(GUI), `PyInstaller` (сборка в .exe). Если для какого-то шага пайплайна
нужен рендеринг JS-страниц — `playwright` как крайняя мера, не по
умолчанию (он тяжёлый и медленный, используй только там, где httpx
объективно не справляется).

## Требования к безопасности и гигиене данных (обязательный чек-лист)

Это отдельно и явно, потому что в референсном проекте были найдены
конкретные проблемы — не повторяй их:

- **TLS-проверка всегда включена.** Никогда не используй `verify=False`
  в httpx/requests. Если конкретный сайт даёт проблему с сертификатом —
  это повод пропустить сайт и залогировать ошибку, а не отключать проверку.
- **Ничего чувствительного не коммитится.** `.gitignore` должен с первого
  коммита включать: `output/`, `artifacts/`, любые `*.settings.json` /
  `*.local.json` с локальными путями пользователя, `.env`, любые Excel-файлы
  с реальными данными клиентов. В референсном проекте файл настроек GUI и
  папка с результатами были случайно закоммичены в публичный репозиторий —
  не повторяй эту ошибку. Если нужен файл-пример конфига — делай
  `config.example.json`, а не реальный `config.json` в репозитории.
- **Секреты — не в коде.** Любые API-ключи (например, если будет
  интеграция с платным API) — через переменные окружения или локальный
  gitignore'нутый конфиг, никогда как строка в исходниках.
- **Атомарная запись Excel.** Пиши во временный файл, валидируй, что он
  открывается, и только потом атомарно переименовывай в целевой файл
  (`os.replace`) — это защищает от повреждения файла при сбое посередине
  записи. Это уже сделано правильно в референсном проекте — используй тот
  же паттерн.
- **Санитайзинг текста перед записью в Excel.** Убирай нелегальные
  XML-символы и обрезай строки до лимита ячейки Excel (32767 символов) —
  готовая функция для этого есть в референсном проекте
  (`sanitize_excel_text`), логику можно взять оттуда.
- **Таймауты и лимиты — на каждом сетевом вызове**, без исключений.
  Ретраи через `tenacity` с небольшим количеством попыток, не бесконечно.
- **Вежливый скрапинг.** Не долби один и тот же сайт/сервис часто и без
  пауз. Официальные API и открытые реестры — приоритет перед скрапингом
  поисковиков; скрапинг поисковой выдачи — крайний случай, а не основной
  механизм поиска (в референсном проекте это было основным механизмом для
  одной из отраслей, и это хрупкое решение — не закладывай так по умолчанию).
- **`subprocess` — только списком аргументов**, никогда `shell=True`.
  Никогда `eval`/`exec` над данными из сети или из файла.
- **GUI-обновления из фоновых потоков — только через безопасный
  диспетчер** (`root.after(...)` в tkinter), никогда напрямую из воркер-треда.

## Юридический момент, который нужно учитывать в дизайне

Приложение будет собирать персональные данные конкретных физлиц (ФИО,
личный email/телефон), а не только реквизиты юрлиц. Заложи в модель данных
для каждого контакта: источник, дату сбора, и предусмотри команду/функцию
удаления записи по запросу. Это не блокирует разработку, но пусть будет
предусмотрено архитектурно с самого начала, а не добавляется потом.

## Тестирование

Пиши `pytest`-тесты сразу вместе с каждым модулем, не откладывай на конец.
Обязательно покрывай тестами: regex-извлечение контактов, логику
классификации/скоринга, логику маршрутизации по шагам пайплайна (что
именно решает пайплайн на каждом шаге и почему). Все сетевые вызовы и
браузер — мокать, не дёргать реальные сайты в тестах.

## Порядок работы

1. Сначала `ARCHITECTURE.md` с деревом решений и структурой модулей — на
   согласование.
2. После подтверждения: engine (модели, excel_io, http_client с
   таймаутами/ретраями) + тесты на него.
3. Каждый шаг пайплайна — отдельным модулем с тестами, начиная с самых
   надёжных источников (Контур-импорт, сопоставление бренда, обход сайта)
   и только потом слабоструктурированные источники.
4. Оркестратор, который прогоняет цепочку и логирует переходы между шагами.
5. GUI поверх готового и протестированного пайплайна, тонкий, без бизнес-логики внутри виджетов.
6. Сборка в `.exe` через PyInstaller, по образцу `build_gui_exe.ps1` из
   референсного проекта (там сделана аккуратная схема с проверкой хешей —
   можно взять за основу).
7. Перед тем как считать задачу выполненной — пройди весь чек-лист
   безопасности выше по каждому написанному модулю.
